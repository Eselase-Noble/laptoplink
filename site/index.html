Move files
straight across.

A from-scratch tool for sending files and folders directly between your own computers. Encrypted end to end, verified byte for byte, and able to resume when the network blinks.

Get the code Quickstart 
# on the receiving machine
$ laptoplink receive --dest ~/incoming --accept-new

# on the sending machine
$ laptoplink send ./ubuntu.iso --to 192.168.1.50
  100.0%   4.7 GiB   283.0 MiB/s   ubuntu.iso
  Done: 1 file(s), 4.7 GiB sent, verified.

Built security-first, then made fast

// no home-rolled crypto, no data held in memory, nothing trusted until it verifies

01

Encrypted & authenticated

A Noise XX handshake proves both machines by their keys, then ChaCha20-Poly1305 protects every byte. Identity is a key, never an IP address.

02

Verified byte for byte

Every chunk is BLAKE3-checked before it touches disk, and the whole file is checked again before it is committed with an atomic rename.

03

Resumable

If a transfer drops, run it again. The receiver asks only for the chunks it is still missing. Nothing that already arrived is sent twice.

04

Flat memory

Everything streams. A one terabyte file uses the same memory as a one megabyte file, bounded no matter how large the transfer gets.

05

rsync-style sync

Keep a folder in sync, skipping files already there. When a big file changed a little, delta transfer sends only the blocks that differ.

06

Safe by construction

Path traversal, absolute paths, and symlink tricks are refused. Deletion during sync is opt-in, confirmed, and only after transfers succeed.

Quickstart

// you need a Rust toolchain, 1.80 or newer

  1. git clone https://github.com/Eselase-Noble/laptoplink.git && cd laptoplink

    Grab the source.

  2. cargo build --release

    The binary lands at target/release/laptoplink. Builds on Linux, macOS, and Windows.

  3. laptoplink receive --dest ~/incoming --accept-new

    On the receiving machine. It prints its address and fingerprint.

  4. laptoplink send ./bigfile.iso --to 192.168.1.50

    On the sending machine. Watch the live rate, then find the verified file waiting on the other side.

Trust, spelled out

// pairing is explicit, and the threat model says what is not yet protected

Machines are identified by a cryptographic key, not an IP address, so nobody can impersonate a device you trust just by taking its address. The receiver turns away unknown machines by default. For the strongest guarantee you read the short fingerprint to each other over a channel you already trust and pair it by hand, which defeats even a machine in the middle on the first connection.

Being honest: this is local-network software today. Transfers across the internet, NAT traversal, relays, and storing keys in the OS keystore are on the roadmap, not done. The threat model in the repo lists every limitation plainly.
